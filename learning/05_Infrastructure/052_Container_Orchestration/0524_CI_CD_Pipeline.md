# CI/CDパイプライン：ソフトウェアデリバリーの自動化された高速道路

## 🎯 この章で学ぶこと
- CI (継続的インテグレーション) と CD (継続的デリバリー/デプロイメント) の違いと、それぞれの目的を明確に説明できる。
- CI/CDパイプラインが、なぜ現代の高速なソフトウェア開発に不可欠なのかを理解する。
- GitHub Actionsを例に、CI/CDパイプラインの基本的な構成要素（イベント、ジョブ、ステップ、アクション）を学ぶ。
- Gitのプッシュをトリガーに、自動的にテスト、Dockerイメージのビルド、レジストリへのプッシュが行われる一連の流れを理解する。
- 本番環境へのデプロイを自動化するCDの概念と、その実現がもたらす価値とリスクを学ぶ。

## 🤔 なぜ重要なのか
あなたが書いたコードが、ユーザーの元に届くまでには、数多くのステップが必要です。コードのビルド、単体テスト、結合テスト、Dockerイメージの作成、セキュリティスキャン、ステージング環境へのデプロイ、そして最後に本番環境へのデプロイ…。これらの作業を毎回手動で行うとどうなるでしょうか？

プロセスは遅く、ヒューマンエラーが頻発し、開発者は「デプロイ」という退屈でリスクの高い作業に多くの時間を奪われます。その結果、新しい機能のリリースは数週間、時には数ヶ月に一度となり、ビジネスのスピードについていけなくなります。

**CI/CDパイプライン**は、このプロセスを完全に自動化するための「高速道路」です。開発者がコードをGitリポジトリにプッシュすると、その変更はベルトコンベアに乗せられ、テスト、ビルド、デプロイといった各工程を自動で通過し、品質が保証された上で、迅速かつ安全にユーザーの元へと届けられます。

例えるなら、手作業で自動車を組み立てるのではなく、自動化された生産ラインで自動車を製造するようなものです。品質は均一化され、生産速度は劇的に向上します。CI/CDを導入することは、開発チームの生産性を飛躍的に高め、ビジネスの競争力を直接左右する、現代ソフトウェア開発における必須の戦略なのです。AIに「デプロイ手順を教えて」と聞くのではなく、「このリポジトリにCI/CDパイプラインを構築して」と指示できることこそ、プロフェッショナルなエンジニアの証です。

## 📚 基礎概念の理解

### CI (Continuous Integration：継続的インテグレーション)
- **概念**: 複数の開発者が書いたコードを、頻繁に（理想的には1日に何度も）メインのブランチにマージし、そのたびに**ビルドと自動テストを実行する**プラクティス。
- **目的**:
    - **統合エラーの早期発見**: コードの競合や、異なる変更間の互換性の問題を、問題が小さいうちに発見し修正する。
    - **コード品質の維持**: 常に自動テストが通る状態を保つことで、リポジトリの健全性を維持する。
- **CIがなければ…**: 各自がローカルで長く開発を続けた後でマージしようとすると、巨大なコンフリクトやバグが発生し、その解決に数日を要する「マージ地獄」に陥る。

### CD (Continuous Delivery/Deployment：継続的デリバリー/デプロイメント)
- **概念**: CIのプラクティスをさらに推し進め、テストをパスしたコードを**いつでも本番環境にリリースできる状態**に保つこと。
- **2つのCD**:
    1.  **継続的デリバリー (Continuous Delivery)**: 本番へのリリース準備ができた成果物（例: Dockerイメージ）を自動で作成し、**最終的な本番デプロイの判断（ボタンを押すなど）は人間が行う**。
    2.  **継続的デプロイメント (Continuous Deployment)**: メインブランチへのマージ後、全ての自動テストをパスしたら、**人間の介在なしに自動で本番環境までデプロイする**。
- **目的**:
    - **リリースの高速化**: 新しい機能やバグ修正を、数週間や数ヶ月ではなく、数日あるいは数時間単位でユーザーに届ける。
    - **リスクの低減**: 一度にリリースする変更が小さくなるため、問題が発生した際の原因特定や切り戻しが容易になる。

## 💡 実践的な活用：GitHub Actions入門

現在最も広く使われているCI/CDツールの一つが、**GitHub Actions**です。GitHubリポジトリにネイティブに統合されており、`.github/workflows`ディレクトリにYAMLファイルを置くだけで簡単に利用を開始できます。

### GitHub Actionsの基本要素
- **Workflow (ワークフロー)**: パイプライン全体を定義するYAMLファイル。
- **Event (イベント)**: ワークフローを起動するきっかけ（トリガー）。例: `on: [push]`（プッシュされた時）、`on: [pull_request]`（プルリクエストが作成された時）。
- **Job (ジョブ)**: ワークフローを構成する一連のステップの集まり。ジョブは独立した仮想環境（ランナー）で実行されます。
- **Step (ステップ)**: ジョブ内の個々のタスク。コマンドを実行したり、`action`を呼び出したりします。
- **Action (アクション)**: ワークフローで再利用可能なコマンドのまとまり。GitHub Marketplaceで公開されている豊富なアクション（例: `actions/checkout`, `docker/build-push-action`）を利用できます。

### ハンズオン：シンプルなCIパイプラインの作成
- **課題**: `main`ブランチにコードがプッシュされたら、自動でテストを実行し、成功したらDockerイメージをビルドしてDocker Hubにプッシュするワークフローを作成します。
- **手順**: `.github/workflows/ci.yml` を作成
    ```yaml
    name: CI Pipeline

    on:
      push:
        branches: [ main ] # mainブランチへのpushをトリガー

    jobs:
      build-and-push:
        runs-on: ubuntu-latest # 実行環境

        steps:
        - name: 1. Checkout repository # リポジトリのコードをチェックアウト
          uses: actions/checkout@v3

        - name: 2. Run tests # テストを実行
          run: |
            npm install
            npm test

        - name: 3. Login to Docker Hub # Docker Hubにログイン
          uses: docker/login-action@v2
          with:
            username: ${{ secrets.DOCKERHUB_USERNAME }} # GitHubのSecrets機能で安全に管理
            password: ${{ secrets.DOCKERHUB_TOKEN }}

        - name: 4. Build and push Docker image # イメージをビルドしてプッシュ
          uses: docker/build-push-action@v3
          with:
            context: .
            push: true
            tags: your-username/my-awesome-app:latest
    ```
- **期待される結果**: このファイルをリポジトリに追加し、`DOCKERHUB_USERNAME`と`DOCKERHUB_TOKEN`をGitHubのSecretsに設定しておけば、`main`ブランチにプッシュするたびに、このパイプラインが自動で実行されます。GitHubの「Actions」タブで、その実行状況やログを確認できます。

## 🔍 深掘り：プロの視点

### GitFlowからGitHub Flow/Trunk-Based Developmentへ
- **背景**: CI/CDの普及は、Gitのブランチ戦略にも大きな影響を与えました。かつて主流だった`develop`ブランチや`release`ブランチを持つ**GitFlow**は、リリースサイクルが長く、CI/CDとの相性があまり良くありません。
- **現代的なブランチ戦略**:
    - **GitHub Flow**: `main`ブランチと機能ブランチのみ。機能ブランチから`main`へのプルリクエストがマージされると、即座に本番へデプロイされます（継続的デプロイメント）。
    - **Trunk-Based Development**: 全ての開発者が単一の`main`(trunk)ブランチに直接コミットします。プルリクエストさえ使いません。これは、非常に高頻度なインテグレーションを強制し、究極のCIプラクティスと言えますが、高度なテスト自動化とチームの習熟が求められます。
- **共通点**: いずれも、メインブランチへの統合を可能な限り高頻度に行い、リリースまでのリードタイムを短縮することを目指しています。

### DevOpsとCI/CD
- **DevOps**: 開発(Dev)と運用(Ops)が密に連携・協力し、ビジネス価値をより迅速かつ確実に提供するための文化・プラクティスです。
- **CI/CDとの関係**: CI/CDパイプラインは、DevOpsの文化を実現するための**技術的な中核**です。開発チームが作ったものを、運用チームが迅速かつ安全に本番環境へ届け、そのフィードバックをまた開発チームに返す、というサイクルを高速に回すための自動化基盤がCI/CDなのです。

## 📋 まとめとチェックポイント
- **CI**は、ビルドとテストを自動化し、統合エラーを早期に発見するためのプラクティス。
- **CD**は、CIを拡張し、いつでもリリース可能な状態を保つ（デリバリー）、あるいは自動でリリースする（デプロイメント）ためのプラクティス。
- CI/CDパイプラインは、ソフトウェアデリバリーの速度と品質を両立させるための自動化された高速道路。
- **GitHub Actions**は、YAMLファイルでワークフローを定義するだけで、強力なCI/CDを実現できるツール。
- 現代の高速な開発では、CI/CDを前提とした**GitHub Flow**のようなシンプルなブランチ戦略が好まれる。
