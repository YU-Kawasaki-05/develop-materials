# 監視とロギング：システムの健康状態を把握する計器盤

## 🎯 この章で学ぶこと
- 監視(Monitoring)とロギング(Logging)の役割の違いと、両者がどう連携するのかを説明できる。
- 可観測性(Observability)の3本柱である「メトリクス」「ログ」「トレース」の概念を理解する。
- SLI, SLO, SLAの違いを理解し、なぜビジネス目標に基づいた監視が重要なのかを学ぶ。
- PrometheusとGrafanaを使ったモダンなメトリクス監視のアーキテクチャ概要を理解する。
- 構造化ロギングの重要性と、それによってどのようにログ分析が効率化されるかを学ぶ。

## 🤔 なぜ重要なのか
あなたは最新鋭の機能を搭載したアプリケーションを、完璧なCI/CDパイプラインを通じて本番環境にデプロイしました。しかし、数時間後、ユーザーから「サイトが遅い」「エラーが出る」という問い合わせが殺到します。あなたはどうしますか？

- サーバーのCPU使用率は？メモリは足りているか？
- エラーはどの機能で、どのくらいの頻度で発生しているのか？
- ユーザーのリクエストは、システムのどこで時間がかかっているのか？

これらの問いに答えられないとしたら、あなたは暗闇の中で手探りで原因を探すしかありません。それはエンジニアリングではなく、ギャンブルです。

**監視とロギング**は、本番環境で稼働する複雑なシステムという「ブラックボックス」の内部を可視化し、その健康状態をリアルタイムで把握するための「計器盤」であり「フライトレコーダー」です。問題が発生したときに迅速に原因を特定し、対処するためだけでなく、問題が表面化する前にその予兆を検知し、プロアクティブ（能動的）に障害を防ぐためにも不可欠です。

例えるなら、医者が患者を診察する際に、体温や血圧を測り（メトリクス監視）、問診で症状を聞き（ログ分析）、必要であればCTスキャンで血流を見る（トレース）ようなものです。これらの情報なしに的確な診断（原因特定）ができないのと同じように、監視とロギングなしに健全なシステム運用はありえません。DevOps文化において、開発チームは自分たちが作ったシステムの運用にも責任を持ちます。その責任を果たすための「目」と「耳」となるのが、監視とロギングなのです。

## 📚 基礎概念の理解

### 可観測性 (Observability) の3本柱
現代的なシステム監視の文脈では、**可観測性 (Observability)**という言葉がよく使われます。これは、システムの内部状態を、外部から得られるデータ（出力）だけを元に、どれだけよく理解できるか、という性質を指します。そのための主要なデータソースが以下の3つです。

1.  **メトリクス (Metrics)**
    - **概念**: 一定間隔で収集される**数値データ**。システムのパフォーマンスや健康状態を示す指標。
    - **例**: CPU使用率、メモリ使用量、リクエスト数、エラーレート、レイテンシ。
    - **特徴**: 軽量で集計しやすく、傾向分析やアラート設定に適している。「何かがおかしい」という**兆候**を知るのに役立つ。

2.  **ログ (Logs)**
    - **概念**: システム内で発生した特定のイベントを記録した、タイムスタンプ付きの**テキストデータ**。
    - **例**: アクセスログ、エラーログ、アプリケーションのデバッグ情報。
    - **特徴**: 詳細なコンテキスト情報を含み、特定の問題の**根本原因**を調査するのに不可欠。「なぜおかしいのか」を突き止めるための証拠。

3.  **トレース (Traces)**
    - **概念**: 分散システム（マイクロサービスなど）において、単一のリクエストが複数のサービスをまたいで処理されていく**経路を可視化**したもの。
    - **例**: ユーザーが商品を注文した際に、リクエストが認証サービス→商品サービス→決済サービスをどう渡っていったかの記録。
    - **特徴**: システム全体のボトルネックや、サービス間の依存関係に起因する問題を特定するのに強力。「どこで問題が起きているのか」を明らかにする。

```mermaid
graph TD
    A[ユーザーリクエスト] --> B{システム}
    subgraph "Observability"
        B -- "時系列の数値データ" --> C(メトリクス<br/>例: エラーレート 5%)

      C -- "兆候の検知" --> F{"何かがおかしい"}

      F -- "ボトルネックの特定" --> E
    end
```

### SLI, SLO, SLA：ビジネスと監視を繋ぐ言葉
- **SLI (Service Level Indicator / サービスレベル指標)**:
    - **定義**: サービスのパフォーマンスを測るための**具体的な指標**。メトリクスの中から選ばれる。
    - **例**: リクエストの成功率、99パーセンタイルレイテンシ。
- **SLO (Service Level Objective / サービスレベル目標)**:
    - **定義**: SLIが達成すべき**目標値**。内部的な目標であり、ユーザーとの契約ではない。
    - **例**: 月間のリクエスト成功率が99.9%であること。
- **SLA (Service Level Agreement / サービスレベル合意)**:
    - **定義**: SLOを達成できなかった場合に、ペナルティ（返金など）が発生する、**ユーザーとの法的な契約**。通常、SLOよりも緩い目標が設定される。
    - **例**: 月間のリクエスト成功率が99.5%を下回った場合、利用料金の10%を返金する。

なぜこれらが重要か？「CPU使用率が80%を超えたらアラート」というような技術的な指標だけに頼った監視は、ビジネスインパクトと直結しません。SLOベースの監視（例：「エラーレートが目標を超え、このままだと月次SLOを達成できない」といったアラート）を行うことで、チームは本当に重要な問題に集中できます。

## 💡 実践的なツールとテクニック

### メトリクス監視：Prometheus & Grafana
- **Prometheus**: メトリクスの収集、保存、クエリ、アラートを行うためのオープンソースツール。時系列データベースとして機能する。デファクトスタンダード。
- **Grafana**: Prometheusなどが収集したメトリクスを、リッチなダッシュボードで可視化するためのツール。
- **アーキテクチャ**: 各アプリケーションやサーバーは、自身のメトリクス（例: `/metrics` エンドポイント）を公開する。Prometheusは、それらのエンドポイントを定期的に**プル (Pull)**してデータを収集する。GrafanaはPrometheusに問い合わせてグラフを描画する。

### ロギング：構造化ロギング
- **Bad 👎**: 人間が読むことだけを考えた、フォーマットがバラバラなログ。
    ```
    ERROR: Failed to process user 123 due to connection timeout.
    ```
- **Good 👍**: 機械がパースしやすいように、JSONなどの構造化されたフォーマットで出力する**構造化ロギング**。
    ```json
    {
      "timestamp": "2023-10-27T12:00:00Z",
      "level": "error",
      "message": "Failed to process user",
      "user_id": 123,
      "reason": "connection_timeout"
    }
    ```
- **利点**: `level`が`error`で、かつ`reason`が`connection_timeout`のログを全て検索する、といった高度な集計や分析が容易になる。**Fluentd**のようなログ収集ツールで集約し、**Elasticsearch**のような検索エンジンに投入するのが一般的。

## 🔍 深掘り：プロの視点

### アラートの哲学：「意味のあるアラートだけを鳴らす」
- **アラート疲れ (Alert Fatigue)**: 重要でないアラートが頻繁に鳴ると、エンジニアはオオカミ少年効果で本当に重要なアラートまで無視するようになる。
- **良いアラートとは**:
    - **緊急性**: 今すぐ人間が対応する必要があるか？
    - **重要性**: ユーザー影響やSLO違反に直結するか？
    - ** actionable**: アラートを受け取った人が、何をすべきか明確にわかるか？
- **理想**: システムは可能な限り自己修復すべきであり、アラートは最後の手段。CPU使用率が高いだけでアラートを鳴らすのではなく、それによってSLOで定めたレイテンシが悪化した場合に初めてアラートを鳴らすべき。

### カオスエンジニアリング (Chaos Engineering)
- **概念**: 本番環境で意図的に障害（サーバーの停止、ネットワークの遅延など）を発生させ、システムがそれにどう耐えるかを実験し、未知の弱点を発見するためのプラクティス。
- **目的**: 監視や自己修復機能が本当に機能するのか、人間が介在しなくてもサービスが継続できるのかを、実際の障害が起こる前に検証する。Netflixが有名。

## 📋 まとめとチェックポイント
- 可観測性の3本柱は**メトリクス**（数値）、**ログ**（記録）、**トレース**（経路）。
- **SLI**（指標）、**SLO**（目標）、**SLA**（契約）は、ビジネス目標と技術的な監視を結びつける。
- メトリクス監視のデファクトスタンダードは**Prometheus**と**Grafana**の組み合わせ。
- ログは**構造化ロギング**にすることで、機械的な分析が劇的に効率化される。
- アラートは「緊急かつ重要で、対応可能な」ものに絞り、アラート疲れを防ぐ。
