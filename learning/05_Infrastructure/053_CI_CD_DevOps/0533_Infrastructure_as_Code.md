# Infrastructure as Code (IaC): インフラをコードで管理する革命

## 🎯 この章で学ぶこと
- なぜ手作業でのインフラ管理（"雪の結晶"サーバー）が問題なのか、その理由を説明できる。
- IaCの基本原則である「宣言的アプローチ」と「冪等性（べきとうせい）」を理解する。
- IaCがもたらす主要なメリット（再現性、バージョン管理、自動化）を具体的なシナリオと関連付けて学ぶ。
- 代表的なIaCツールであるTerraformの役割と、その基本的な使い方（リソース定義、plan, apply）を理解する。
- IaCがDevOps文化とCI/CDパイプラインにおいて、どのように中心的な役割を果たすかを学ぶ。

## 🤔 なぜ重要なのか
あなたは新しいプロジェクトのために、クラウド上にWebサーバー、アプリケーションサーバー、データベースをセットアップする必要があります。あなたはどうしますか？

**伝統的なアプローチ**: クラウドの管理コンソール画面を開き、マニュアルや記憶を頼りに、一つ一つポチポチとクリックしてサーバーを作成し、ネットワークを設定し、ファイアウォールルールを追加していくでしょう。数時間後、なんとか環境はできあがりました。しかし、3ヶ月後に同じ環境をもう一つ作れますか？昨日の設定変更の理由を正確に覚えていますか？このサーバーは、他の誰かが微妙に設定を変えてしまった「世界に一つだけのサーバー」（**雪の結晶サーバー**）になってはいないでしょうか？

このような手作業によるインフラ管理は、ヒューマンエラーの温床であり、再現性がなく、変更履歴も追えません。インフラが複雑になるほど、管理は破綻します。

**Infrastructure as Code (IaC)**は、この問題を根本から解決する革命的なプラクティスです。インフラの構成（サーバーの種類、ネットワークの設定、ロードバランサーのルールなど）を、アプリケーションのコードと同じように、**テキストファイル（コード）として記述し、バージョン管理する**のです。

例えるなら、秘伝のタレを「料理人の勘」に頼って作るのではなく、誰でも同じ味を再現できるように、材料と手順を全てレシピ（コード）に書き起こすようなものです。IaCによって、インフラは「職人技」の世界から、「科学的で再現可能なエンジニアリング」の世界へと進化します。AIに「本番環境と同じ構成のテスト環境を作って」と依頼すれば、AIは管理画面をクリックする手順書ではなく、IaCのコードを生成するでしょう。IaCは、現代のクラウド活用における必須教養なのです。

## 📚 基礎概念の理解

### IaCの基本原則
- **宣言的アプローチ (Declarative Approach)**:
    - **概念**: 「Webサーバーが3台あり、このロードバランサーにぶら下がっている」という**最終的にあるべき状態**をコードで宣言する。
    - **対義語**: 命令的アプローチ（「Webサーバーを1台作れ」「次にネットワークを設定せよ」と手順を指示する）。
    - **利点**: 現在の状態がどうであれ、ツールが差分を自動で計算し、宣言された状態になるようにインフラを変更してくれる。開発者は複雑な手順を意識する必要がない。

- **冪等性 (Idempotency)**:
    - **概念**: 同じIaCコードを何度実行しても、インフラの状態が同じ結果になるという性質。
    - **例**: 3台のサーバーを定義したコードを実行すると、サーバーが存在しなければ3台作成され、既に3台存在すれば何も起こらない。サーバーが2台しか なければ1台追加される。
    - **利点**: これにより、安心して何度でもIaCの適用コマンドを実行できる。CI/CDパイプラインでの自動実行には不可欠な性質。

### IaCがもたらす価値
- **再現性 (Reproducibility)**: 同じコードから、いつでも、誰でも、全く同じ構成のインフラを再現できる。開発環境、ステージング環境、本番環境の一貫性を保つことが容易になる。
- **バージョン管理 (Version Control)**: インフラの構成をGitで管理できる。`git diff`で変更差分を確認し、`git blame`で誰がいつなぜ変更したかを追跡し、問題があれば`git revert`で過去の構成に安全に戻すことができる。
- **自動化 (Automation)**: IaCコードをCI/CDパイプラインに組み込むことで、インフラの構築、変更、破棄を完全に自動化できる。プルリクエストでインフラの変更をレビューし、マージされたら自動で本番環境に適用する、といった**GitOps**的なワークフローが可能になる。

## 💡 実践的な活用：Terraform入門
IaCを実現するためのツールは数多くありますが、現在最も広く使われているのがHashiCorp社の**Terraform**です。特定のクラウドに依存せず、AWS, Azure, Google Cloudなど様々なプロバイダーに対応しているのが大きな特徴です。

### Terraformの主要な概念
- **Provider (プロバイダー)**: 操作対象のプラットフォーム（AWS, Azure, Docker, GitHubなど）。
- **Resource (リソース)**: プロバイダー内で管理されるインフラの構成要素（例: AWSのEC2インスタンス、S3バケット）。
- **HCL (HashiCorp Configuration Language)**: Terraformの設定を記述するための、人間にも読みやすい独自の言語。

### ハンズオン：Terraformでサーバーを1台立てる
- **課題**: AWS上にシンプルなWebサーバー（EC2インスタンス）を1台作成する。
- **手順**:
    1.  `main.tf`というファイルを作成する。
    ```hcl
    # main.tf

    # 1. 使用するプロバイダー（この場合はAWS）を定義
    provider "aws" {
      region = "ap-northeast-1" # 東京リージョン
    }

    # 2. 作成したいリソースを定義
    resource "aws_instance" "web_server" {
      ami           = "ami-0c55b159cbfafe1f0" # Amazon Linux 2のAMI ID
      instance_type = "t2.micro"             # インスタンスタイプ

      tags = {
        Name = "MyWebServer-Terraform"
      }
    }
    ```
    2.  Terraformのコマンドを実行する。
        -   `terraform init`: 必要なプロバイダーのプラグインをダウンロードし、作業ディレクトリを初期化する。最初に1回だけ実行。
        -   `terraform plan`: コードが現在のインフラに対してどのような変更（作成、変更、破棄）を行うかを表示する。**インフラに実際の変更は加えない**ため、安全に実行できる。
        -   `terraform apply`: `plan`で表示された変更計画を、実際にインフラに適用する。

- **期待される結果**: `terraform apply`を実行すると、AWS上に`MyWebServer-Terraform`という名前のEC2インスタンスが作成されます。その後、もう一度`terraform plan`を実行すると、「変更はありません」と表示され、冪等性が確認できます。

## 🔍 深掘り：プロの視点

### ツールの選択：Terraform vs CloudFormation vs Ansible
- **Terraform**: マルチクラウド対応。独自のHCL言語。状態を`tfstate`ファイルで管理。デファクトスタンダード。
- **AWS CloudFormation**: AWS専用。YAML/JSONで記述。AWSとの統合が深い。Terraformに比べて機能追加が早い場合がある。
- **Ansible**: 本来は構成管理ツール（サーバーにSSHで接続し、ミドルウェアのインストールなどを行う）。インフラのプロビジョニングも可能だが、宣言的というよりは命令的な側面が強い。

一般的に、クラウドインフラの**プロビジョニング（作成・管理）**にはTerraformやCloudFormationを、その後のOSやミドルウェアの**構成管理**にはAnsibleを使う、というように組み合わせて利用されることが多いです。

### 状態管理 (State Management)
- **tfstateファイル**: Terraformは、自分が管理しているリソースの情報を`.tfstate`というファイルに保存します。このファイルは、Terraformが次に何をするべきか（何を作成し、何を更新し、何を削除するか）を知るための「地図」であり、非常に重要です。
- **リモートステート**: チームでIaCを実践する場合、この`tfstate`ファイルを各個人のローカルマシンに置くのではなく、AWS S3のような共有ストレージで一元管理（**リモートステート**）する必要があります。これにより、チームメンバー全員が同じ状態を参照し、意図しない衝突を防ぐことができます。

## 📋 まとめとチェックポイント
- IaCは、インフラ構成をコードとして記述し、バージョン管理するプラクティス。
- 手作業による管理（**雪の結晶サーバー**）を防ぎ、インフラの**再現性**、**追跡可能性**、**自動化**を実現する。
- **宣言的アプローチ**と**冪等性**がIaCツールの重要な原則。
- **Terraform**は、マルチクラウド対応のIaCツールのデファクトスタンダード。
- `terraform init`, `plan`, `apply`が基本的なワークフロー。
- IaCはCI/CDパイプラインと組み合わせることで、インフラの変更も含めた完全な自動化を実現する。
