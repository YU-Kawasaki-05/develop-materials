# 第23章 APIセキュリティの要点

## 🎯 この章で学ぶこと
- APIセキュリティがなぜWebアプリケーション全体のセキュリティにおいてクリティカルなのかを理解する。
- OWASP API Security Top 10の主要な脆弱性（特にBroken Object Level Authorization）を説明できる。
- APIキー、OAuth 2.0、JWT（JSON Web Token）といった認証・認可技術の役割と使い分けを理解する。
- レート制限や入力バリデーションが、なぜAPIの防御において重要なのかを説明できる。
- 安全なAPIを設計・実装するための具体的なベストプラクティスを適用できる。

## 🤔 なぜ重要なのか
APIは現代のアプリケーションの「神経系」です。フロントエンドとバックエンド、あるいはサービス間でデータをやり取りする中心的な役割を担っています。しかし、それは同時に、攻撃者にとって最も魅力的で、狙いやすい攻撃対象の一つであることを意味します。

Webサイトの入力フォームを保護するように、APIのエンドポイントも厳重に保護しなければ、重大な情報漏洩やデータ改ざんにつながります。特に、APIはプログラムから直接利用されるため、人間が操作するUIよりもはるかに高速かつ大量のリクエストを送信でき、一度脆弱性が見つかると被害は甚大なものになりがちです。

AIに「APIを作って」と指示するだけでは、セキュリティが考慮されたコードは生成されません。「このエンドポイントは認可が必要で、このパラメータは厳密にバリデーションして」といった具体的な指示を出すためには、APIセキュリティの知識が不可欠です。安全なAPIを構築する能力は、信頼されるエンジニアであるための必須条件です。

## 📚 基礎概念の理解

### OWASP API Security Top 10
OWASP (The Open Web Application Security Project) は、Webセキュリティに関する情報を提供する世界的なコミュニティです。彼らが発表している「APIセキュリティ・トップ10」は、APIにおける最も一般的で危険な脆弱性をまとめたものです。ここでは特に重要なものをいくつか紹介します。

1.  **BOLA (Broken Object Level Authorization) / IDOR (Insecure Direct Object References) - オブジェクトレベル認可の不備**
    -   **最も重要かつ頻発する脆弱性**。
    -   **事象**: ユーザーが、自分にアクセス権のないはずの他人のデータ（オブジェクト）を、IDを推測して操作できてしまう。
    -   **例**: `/users/123/profile` の `123` の部分を `456` に書き換えるだけで、他人のプロフィールを閲覧・編集できてしまう。
    -   **原因**: 「認証（ログインしているか）」は確認しているが、「認可（そのデータへのアクセス権があるか）」を確認していない。

2.  **認証の不備 (Broken Authentication)**
    -   認証メカニズム自体が脆弱であるケース。
    -   **例**: パスワードリセット機能が悪用しやすい、JWTの検証が不十分、有効期限のないAPIキーを使っているなど。

3.  **過剰なデータ公開 (Excessive Data Exposure)**
    -   APIが、クライアント（UI）で必要とされている以上の情報を返してしまう。
    -   **例**: ユーザー詳細APIが、画面には表示しないハッシュ化済みパスワードや個人情報まで含んで返してしまう。UI側でフィルタリングしても、レスポンス自体を見られれば漏洩する。

4.  **レート制限の欠如 (Lack of Resources & Rate Limiting)**
    -   短時間に大量のリクエストを受け付けることで、サービスが停止したり、ブルートフォース攻撃（総当たり攻撃）を許してしまったりする。

5.  **一括割り当ての不備 (Mass Assignment)**
    -   クライアントから送られてきたJSONを、内部のデータオブジェクトに無検証でマッピングしてしまう。
    -   **例**: ユーザーが自分の名前を変更するAPIで、リクエストに `"isAdmin": true` というフィールドをこっそり含めて送信すると、管理者権限を奪取できてしまう。

### APIの認証 (Authentication) vs 認可 (Authorization)
この2つの違いを正確に理解することが、セキュリティの第一歩です。
- **認証**: 「あなたは誰ですか？」。通信の相手が、本人であることを確認するプロセス。
    - 例: ログインIDとパスワード、APIキー、生体認証。
- **認可**: 「あなたは何ができますか？」。認証されたユーザーが、特定のリソースに対してどのような操作（読み取り、書き込みなど）を許可されているかを確認するプロセス。
    - 例: 管理者ユーザーは全ユーザーのデータを編集できるが、一般ユーザーは自分のデータしか編集できない。

**BOLA/IDORは、まさにこの「認可」のチェック漏れによって発生します。**

### 主要な認証・認可技術
-   **APIキー**:
    -   サーバーが発行するシンプルな文字列。クライアントはリクエスト時にこれをヘッダーなどに含める。
    -   主に、クライアントアプリケーション自体を識別するために使われる。個々のエンドユーザーの認証には向かない。
-   **OAuth 2.0**:
    -   **認可**のためのフレームワーク。「Facebookアカウントでログイン」のように、ユーザーに代わってサードパーティアプリケーションがリソースにアクセスする権限を与える仕組み。
    -   アクセストークンを発行し、クライアントはこれを使って保護されたリソースにアクセスする。
-   **JWT (JSON Web Token)**:
    -   ユーザー情報や権限情報（クレーム）をJSON形式で含み、かつ電子署名によって改ざんを検知できるトークン。
    -   サーバーはリクエストの都度データベースに問い合わせなくても、JWTを検証するだけでユーザーを認証・認可できるため、ステートレスなREST APIと非常に相性が良い。

## 💡 実践的な活用

### ハンズオン：BOLA/IDOR脆弱性の対策
ユーザーが自分の投稿を取得するAPIを例に考えます。
- `GET /posts/{postId}`

**脆弱な実装 (認可チェックなし)**:
```python
# FastAPI (Python) の例
@router.get("/posts/{post_id}")
def read_post(post_id: int, db: Session = Depends(get_db)):
    post = db.query(Post).filter(Post.id == post_id).first()
    if not post:
        raise HTTPException(status_code=404, detail="Post not found")
    # ここに認可のチェックがない！
    return post
```
このコードは、リクエストしてきたユーザーに関係なく、存在する`post_id`であれば誰でも投稿を見れてしまいます。

**安全な実装 (認可チェックあり)**:
```python
@router.get("/posts/{post_id}")
def read_post(
    post_id: int,
    db: Session = Depends(get_db),
    # JWTから現在のユーザー情報を取得する（認証）
    current_user: User = Depends(get_current_user)
):
    post = db.query(Post).filter(Post.id == post_id).first()
    if not post:
        raise HTTPException(status_code=404, detail="Post not found")

    # ★認可チェック: 投稿の所有者が現在のユーザーであるかを確認
    if post.owner_id != current_user.id:
        raise HTTPException(status_code=403, detail="Not enough permissions")

    return post
```
`post.owner_id`と`current_user.id`を比較する、この**たった1行のif文がセキュリティを担保します。**

### APIセキュリティのベストプラクティス

-   **入力バリデーションを徹底する**:
    -   クライアントからの入力は一切信用しない（ゼロトラスト）。
    -   型、長さ、フォーマット、範囲などを厳密にチェックする。
    -   予期しないフィールドは無視するか、エラーにする（一括割り当て対策）。
-   **適切なHTTPステータスコードを返す**:
    -   認証エラーなら `401 Unauthorized`。
    -   認可エラーなら `403 Forbidden`。
    -   存在しないリソースなら `404 Not Found`。
-   **HTTPS (TLS) を常に使用する**:
    -   APIへの通信はすべて暗号化する。これにより、通信経路上での盗聴や改ざんを防ぐ。
-   **CORS (Cross-Origin Resource Sharing) を適切に設定する**:
    -   どのドメインからのフロントエンドリクエストを許可するかを明示的に設定する。ワイルドカード(`*`)での許可は慎重に。
-   **セキュリティヘッダーを設定する**:
    -   `Content-Security-Policy`, `X-Content-Type-Options` などのHTTPヘッダーを設定し、ブラウザのセキュリティ機能を活用する。
-   **機密情報をログに出力しない**:
    -   APIキー、パスワード、個人情報などをログファイルに書き込まない。

## 🔍 深掘り：プロの視点

### 多要素認証 (MFA) とAPI
重要な操作（決済、個人情報変更など）を行うAPIでは、通常の認証に加えて、追加の認証要素（SMSコード、認証アプリのトークンなど）を要求する多要素認証の実装が求められます。
この場合、APIのフローは一度のやり取りでは完結しません。
1.  クライアントが操作をリクエスト。
2.  サーバーは `202 Accepted` のようなステータスと共に、「MFAが必要です」というレスポンスを返す。
3.  クライアントはMFAの入力を促し、MFAコードを別のエンドポイントに送信。
4.  サーバーがMFAコードを検証し、成功すれば最初の操作を完了させる。
このように、状態を管理する必要があり、設計がより複雑になります。

### APIゲートウェイによるセキュリティの一元管理
マイクロサービスアーキテクチャのように、多数のAPIが林立する環境では、個々のサービスでセキュリティ対策を実装するのは非効率で、抜け漏れも発生しやすくなります。
そこで**APIゲートウェイ**を導入し、セキュリティ機能を一元化するアプローチが取られます。
- **APIゲートウェイの役割**:
    -   全てのAPIリクエストの単一の入口となる。
    -   認証・認可
    -   レート制限
    -   ロギング・モニタリング
    -   リクエスト/レスポンスの変換
個々のマイクロサービスはビジネスロジックに集中でき、セキュリティはゲートウェイ層に任せることができます。

## 📋 まとめとチェックポイント
- APIセキュリティの要は「認証」と「認可」。特に、**オブジェクトレベルの認可 (BOLA/IDOR)** のチェック漏れは致命的な脆弱性となる。
- **OWASP API Security Top 10**は、API開発者が知るべき共通の脆弱性リスト。
- クライアントからの入力は一切信用せず、厳密な**バリデーション**を行う。
- JWTはステートレスなAPI認証と相性が良く、OAuth 2.0は第三者アプリケーションへの**認可**を与えるフレームワーク。
- レート制限、HTTPSの強制、適切なCORS設定は、API防御の基本的なベストプラクティス。
