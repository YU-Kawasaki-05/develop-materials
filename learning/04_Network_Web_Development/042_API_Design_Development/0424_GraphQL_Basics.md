# 第24章 GraphQL基礎：RESTとの違いを理解する

## 🎯 この章で学ぶこと
- GraphQLがどのような問題を解決するために生まれたのかを説明できる。
- REST APIにおける「オーバーフェッチ」と「アンダーフェッチ」の問題を具体例で示せる。
- GraphQLの3つの主要な概念「クエリ(Query)」「ミューテーション(Mutation)」「スキーマ(Schema)」の役割を理解する。
- クライアントが欲しいデータを柔軟に指定できる、GraphQLクエリの基本的な書き方を習得する。
- GraphQLが常にRESTより優れているわけではなく、トレードオフが存在することを理解する。

## 🤔 なぜ重要なのか
REST APIは長年にわたりAPI設計の主流でしたが、アプリケーションが複雑化するにつれて、いくつかの課題が明らかになってきました。特に、モバイルアプリのように通信環境が不安定なクライアントや、多様なデータを一度に表示したいフロントエンドにとって、RESTの固定的なデータ構造は扱いにくい場合がありました。

**GraphQL**は、これらの課題を解決するためにFacebook（現Meta）社が開発し、オープンソース化した「APIのためのクエリ言語」です。サーバーサイドのAPI実装方法でもあります。クライアントが**「欲しいデータを、欲しい分だけ」**リクエストできる柔軟性が最大の特徴です。

AIはREST APIもGraphQL APIも生成できますが、どちらの技術を選択すべきか、その判断は人間に委ねられています。それぞれのアーキテクチャの長所と短所を理解し、プロジェクトの要件に最適な技術を選定できることは、AIを使いこなす現代の開発者にとって非常に重要なスキルです。

## 📚 基礎概念の理解

### RESTの課題：オーバー/アンダーフェッチ
GraphQLの利点を理解するために、まずRESTが抱える課題を見てみましょう。

-   **オーバーフェッチ (Over-fetching)**
    -   **事象**: APIレスポンスに、クライアントが必要としない余分なデータまで含まれてしまうこと。
    -   **例**: ユーザーの名前だけが必要なのに、`/users/123`エンドポイントが住所、電話番号、過去の注文履歴など全てのユーザー情報を返してしまう。これはモバイル通信において無駄なデータ転送量となります。

-   **アンダーフェッチ (Under-fetching)**
    -   **事象**: 必要なデータをすべて揃えるために、複数のAPIエンドポイントを何度も呼び出さなければならないこと。
    -   **例**: ブログ記事とその記事についたコメント、そしてコメントしたユーザーの名前を表示したい場合、
        1.  `GET /posts/1` (記事取得)
        2.  `GET /posts/1/comments` (コメントIDリスト取得)
        3.  `GET /users/10`, `GET /users/11`, ... (各コメントユーザーの情報を個別に取得)
        のように、多数のリクエストが必要になる（N+1問題）。これにより、画面表示が遅くなります。

### GraphQLの解決策：クライアントが必要なものを定義する
GraphQLはこれらの問題を、全く異なるアプローチで解決します。
-   **単一のエンドポイント**: 通常、`/graphql`という単一のエンドポイントしか持ちません。
-   **クライアントがクエリを送信**: クライアントは、このエンドポイントに対して、「どのようなデータが欲しいか」を記述した**クエリ**をPOSTリクエストで送信します。
-   **サーバーはクエリ通りに応答**: サーバーは送られてきたクエリを解釈し、その通りの構造でJSONデータを返します。

**GraphQLクエリの例**:
ユーザーID `1` の名前と、そのユーザーの最新3件の投稿のタイトルだけが欲しい場合

```graphql
query {
  user(id: "1") {
    name
    posts(last: 3) {
      title
    }
  }
}
```

**レスポンスの例**:
クエリで要求した通りの構造でデータが返されます。余分なデータ（オーバーフェッチ）も、不足したデータ（アンダーフェッチ）もありません。
```json
{
  "data": {
    "user": {
      "name": "Taro Yamada",
      "posts": [
        { "title": "GraphQL入門" },
        { "title": "RESTとの比較" },
        { "title": "実践的な使い方" }
      ]
    }
  }
}
```

### GraphQLの主要な構成要素

1.  **スキーマ (Schema)**
    -   APIで利用可能なデータの型（オブジェクトの種類、フィールドなど）を厳密に定義したもの。APIの仕様書そのものです。
    -   `User`型には`name`と`email`がある、`Post`型には`title`と`content`がある、といったことを**スキーマ定義言語 (SDL: Schema Definition Language)** を使って記述します。
    -   このスキーマが、クライアントとサーバー間の「契約」となります。

    **スキーマ定義の例**:
    ```graphql
    type User {
      id: ID!
      name: String
      posts: [Post!]
    }

    type Post {
      id: ID!
      title: String
      author: User
    }

    type Query {
      user(id: ID!): User
      posts: [Post!]
    }
    ```

2.  **クエリ (Query)**
    -   データの**読み取り**操作。RESTの`GET`に相当します。
    -   クライアントはスキーマに定義された型とフィールドを組み合わせて、自由にデータの取得方法を指定できます。

3.  **ミューテーション (Mutation)**
    -   データの**書き込み**（作成・更新・削除）操作。RESTの`POST`, `PUT`, `DELETE`に相当します。
    -   クエリと同様の構文で記述しますが、`mutation`キーワードで開始します。

    **ミューテーションの例**:
    ```graphql
    mutation {
      createPost(title: "新しい投稿", content: "本文です") {
        id
        title
      }
    }
    ```
    書き込み操作の後に、どのデータを返してほしいか（この例では新しい投稿の`id`と`title`）も指定できます。

## 💡 実践的な活用

### REST vs GraphQL：どちらを選ぶか？
GraphQLは強力ですが、銀の弾丸ではありません。どちらの技術を選ぶべきかは、プロジェクトの特性によります。

| 特性 | RESTが適しているケース | GraphQLが適しているケース |
| :--- | :--- | :--- |
| **クライアントの種類** | サーバーサイド間の通信、管理画面など、データ要件が固定的な場合。 | モバイルアプリ、多様なコンポーネントを持つフロントエンドなど、クライアントごとに必要なデータが異なる場合。 |
| **データ構造** | リソースの構造がシンプルで、明確に定義されている場合。 | 関連しあう複雑なデータ（グラフ構造）を扱う場合。（例: SNSの友達関係、組織図など） |
| **パフォーマンス** | HTTPキャッシュを最大限活用したい場合。各エンドポイントがキャッシュキーになる。 | クライアント側のデータ取得効率を最大化したい場合。リクエスト回数を最小限に抑える。 |
| **開発のシンプルさ** | 小規模なプロジェクトや、素早くAPIを立ち上げたい場合。コンセプトが広く知られている。 | フロントエンドとバックエンドのチームが分かれていて、仕様の共有を厳密に行いたい場合。 |
| **既存システム** | 既に多くのREST API資産がある場合。 | 新規プロジェクトで、フロントエンドの要求が多岐にわたることが予想される場合。 |

### GraphQLの注意点
-   **キャッシュの複雑性**:
    -   RESTではURI単位でキャッシュできましたが、GraphQLは単一エンドポイントのため、同様の方法は使えません。クライアント側での高度なキャッシュ戦略が必要になります。
-   **ファイルアップロード**:
    -   GraphQLの仕様にはファイルアップロードが定義されておらず、別途ライブラリなどを使って実装する必要があります。
-   **複雑なクエリのパフォーマンス**:
    -   クライアントが非常に深い階層や、重い計算を伴うフィールドを要求するクエリを送信すると、サーバーに過大な負荷がかかる可能性があります。対策として、クエリの深さ制限やタイムアウト設定が必要です。
-   **学習コスト**:
    -   RESTに比べて、チーム全体が新しい概念（スキーマ、クエリ言語など）を学ぶ必要があります。

## 🔍 深掘り：プロの視点

### スキーマファースト開発
GraphQL開発は、スキーマを最初に設計する**スキーマファースト**のアプローチが一般的です。これはRESTにおけるドキュメントファーストと似ていますが、より強制的です。
1.  **スキーマ設計**: まずAPIの全容をスキーマ(SDL)で記述します。これがバックエンドとフロントエンド間の「契約書」になります。
2.  **並行開発**: このスキーマを元に、
    -   バックエンドチームは、各フィールドのデータを返す**リゾルバ (Resolver)** という関数を実装します。
    -   フロントエンドチームは、スキーマから生成されたモックデータを使って、バックエンドの実装を待たずにUI開発を進めます。
3.  **統合**: 両者の実装が完了すれば、スムーズに統合できます。

このアプローチにより、チーム間のコミュニケーションが円滑になり、手戻りが大幅に削減されます。

### マイクロサービスとGraphQL：Federation
複数のマイクロサービスがそれぞれ独自のGraphQLスキーマを持っている場合、それらを統合してクライアントに単一のGraphQL APIとして見せる技術が**Apollo Federation**です。
-   APIゲートウェイが、各マイクロサービスのスキーマを束ねて一つの巨大なグラフを構築します。
-   クライアントからのクエリを解釈し、必要なデータをどのマイクロサービスから取得すべきかを判断して、リクエストを振り分けます。
-   これにより、クライアントは背後の複雑なマイクロサービスアーキテクチャを意識することなく、単一のAPIと対話できます。

## 📋 まとめとチェックポイント
- GraphQLは、クライアントが「欲しいデータを、欲しい分だけ」リクエストできるAPIのためのクエリ言語。
- RESTの「オーバーフェッチ」「アンダーフェッチ」という課題を解決する。
- **スキーマ**でAPIの仕様を定義し、データの読み取りには**クエリ**、書き込みには**ミューテーション**を使用する。
- 単一のエンドポイント（`/graphql`）に対して、クライアントが柔軟なクエリを送信する。
- GraphQLは銀の弾丸ではなく、キャッシュや複雑なクエリの扱いなど、RESTとは異なるトレードオフが存在する。
