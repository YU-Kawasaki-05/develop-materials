# 第21章 REST API設計原則

## 🎯 この章で学ぶこと
- RESTが生まれた背景と、それが解決しようとした課題を理解する。
- RESTの6つのアーキテクチャ原則（制約）を自分の言葉で説明できる。
- リソース指向アーキテクチャ（ROA）の考え方に基づき、APIのエンドポイントを設計できる。
- HTTPメソッド（GET, POST, PUT, DELETEなど）を適切に使い分けられる。
- 冪等性（Idempotency）と安全性の概念を理解し、API設計に活かせる。

## 🤔 なぜ重要なのか
現代のWebサービスは、そのほとんどが「API（Application Programming Interface）」を通じて連携しています。スマートフォンアプリがサーバーと通信するのも、異なる企業のサービスがデータをやり取りするのも、APIがあるからです。その中でも**REST (REpresentational State Transfer)**は、Webの仕組みを最大限に活かした、シンプルで標準的な設計思想として、長年にわたりデファクトスタンダードとなっています。

「とりあえず動くAPI」を作るだけなら、AIでも可能です。しかし、「メンテナンスしやすく、スケール可能で、誰にとっても分かりやすいAPI」を設計するには、RESTの本質的な原則を理解している必要があります。この知識は、あなたが設計する側であれ、利用する側であれ、他のエンジニアと円滑にコミュニケーションをとり、堅牢なシステムを構築するための共通言語となります。

## 📚 基礎概念の理解

### RESTとは何か？：RPCからの脱却
RESTが登場する以前、主流だったのは**RPC (Remote Procedure Call)**という考え方でした。これは「遠隔のサーバーにある関数を、まるでローカルの関数のように呼び出す」というもので、`getUser(123)`や`createPost("ブログタイトル", "本文")`のような形式が一般的でした。一見分かりやすいですが、以下のような問題がありました。
- **手続き的**: `getUser`や`createPost`など、動詞ベースの関数名が無限に増えていく。
- **密結合**: クライアントとサーバーが、特定の関数名や引数に強く依存してしまう。
- **標準の欠如**: 呼び出し規約がシステムごとにバラバラで、学習コストが高い。

これに対し、RESTはWebの生みの親であるRoy Fielding氏が提唱した、全く異なるアプローチです。
**「Webの仕組み（HTTP）をそのまま使えば、もっとシンプルでスケールするシステムが作れるじゃないか」**
これがRESTの根幹思想です。

### RESTの6つの制約（Architectural Constraints）
RESTは具体的な技術ではなく、以下の6つの原則（制約）を満たすアーキテクチャスタイルです。

1.  **クライアント/サーバー分離 (Client-Server)**
    -   UIを持つクライアントと、データを持つサーバーの役割を完全に分離する。これにより、それぞれが独立して進化できる。
    -   例え：レストランで、客（クライアント）はメニューを見て注文するだけで、厨房（サーバー）の内部事情を知る必要はない。

2.  **ステートレス (Stateless)**
    -   サーバーは、クライアントの状態を一切保持しない。リクエストは、それ自体で完結した情報を含んでいる必要がある。
    -   例え：自動販売機は、あなたが前に何を買ったかを覚えていない。毎回お金を入れてボタンを押す必要がある。
    -   **利点**: どのサーバーが応答しても良いため、スケーラビリティが劇的に向上する。

3.  **キャッシュ可能性 (Cacheable)**
    -   レスポンスには、それがキャッシュ可能かどうかを示す情報を含めるべき。
    -   例え：一度見たWebページはブラウザにキャッシュされ、次回の表示が高速化される。
    -   **利点**: サーバーへの不要なリクエストを減らし、パフォーマンスを向上させる。

4.  **階層化システム (Layered System)**
    -   クライアントは、直接通信しているサーバーの先に何があるか（ロードバランサー、プロキシなど）を知らない。
    -   例え：オンラインショップで注文した際、そのリクエストがどの倉庫やどの配送業者に渡っているかを意識しない。
    -   **利点**: セキュリティ向上や負荷分散など、システム構成を柔軟に変更できる。

5.  **統一インターフェース (Uniform Interface)**
    -   これがRESTの最も重要な制約。以下の4つのサブ制約から成る。
        1.  **リソースの識別**: URI (Uniform Resource Identifier) を使って、すべての「リソース」を一意に識別する。（例: `/users/123`）
        2.  **表現によるリソース操作**: リソースの表現（JSONやXMLなど）を取得し、それを操作してサーバーの状態を変更する。
        3.  **自己記述的メッセージ (Self-descriptive Messages)**: メッセージ自体が、その処理方法を理解するための情報を含んでいる。（例: `Content-Type: application/json`）
        4.  **HATEOAS (Hypermedia as the Engine of Application State)**: レスポンスに、次に取りうるアクションへのリンクを含める。（例: ユーザー情報の取得結果に「投稿一覧へのリンク」を含める）

6.  **コードオンデマンド (Code-On-Demand) (任意)**
    -   サーバーがクライアントに実行可能なコード（例: JavaScript）を送信し、クライアントの機能を拡張できる。必須ではない。

### リソース指向アーキテクチャ (ROA)
RESTの中心的な考え方が、「リソース」をどう扱うかです。RPCが「動詞」中心だったのに対し、RESTは**「名詞」中心**です。
- **リソース**: APIが提供する「モノ」。URIで表現される。（例: `ユーザー`, `商品`, `投稿`）
- **操作**: HTTPメソッド（`GET`, `POST`, `PUT`, `DELETE`）で表現される。
- **表現**: リソースの状態をJSONやXMLなどの形式で表現したもの。

| 操作の種類 | HTTPメソッド | URIの例 | 説明 |
| :--- | :--- | :--- | :--- |
| **取得 (Read)** | **GET** | `/users/123` | ID `123`のユーザー情報を取得する |
| **作成 (Create)**| **POST** | `/users` | 新しいユーザーを作成する |
| **更新 (Update)**| **PUT** | `/users/123` | ID `123`のユーザー情報を**全体**更新する |
| **部分更新** | **PATCH** | `/users/123` | ID `123`のユーザー情報を**一部**更新する |
| **削除 (Delete)**| **DELETE** | `/users/123` | ID `123`のユーザー情報を削除する |

このシンプルな対応付けにより、APIの設計が非常に予測しやすくなります。`/users`というURIを見れば、「ユーザーの集合」を扱うエンドポイントだと直感的に理解できます。

## 💡 実践的な活用

### 安全性と冪等性（べきとうせい）
API設計において非常に重要な概念です。

-   **安全性 (Safety)**
    -   **概念**: その操作を何回実行しても、サーバー上のリソースの状態が変化しないこと。
    -   **該当メソッド**: `GET`, `HEAD`, `OPTIONS`
    -   **例**: `/users`を何度GETしても、ユーザーデータは変わらない。

-   **冪等性 (Idempotency)**
    -   **概念**: ある操作を1回実行した場合と、複数回実行した場合の結果が同じであること。
    -   **該当メソッド**: `GET`, `PUT`, `DELETE`
    -   **例**: `/users/123`をDELETEするリクエストを2回送っても、1回目で削除され、2回目は「既に存在しない」となるだけで、結果（ユーザー123がいない状態）は同じ。
    -   **POSTは冪等ではない**: `/posts`に2回POSTすると、2つの新しい投稿が作成されてしまう。

クライアント側でリクエストがタイムアウトした場合、冪等な操作であれば安心してリトライできますが、冪等でない操作（POST）をリトライすると意図しない重複データが発生する可能性があります。

### ハンズオン：良いAPI vs 悪いAPI
SNSの「いいね」機能のAPIを設計してみましょう。

**悪い設計例 (RPCスタイル)**
- `POST /likePost`  (リクエストボディ: `{"userId": 1, "postId": 100}`)
- `POST /unlikePost` (リクエストボディ: `{"userId": 1, "postId": 100}`)
- *問題点*:
    - URIが動詞。
    - どのリソースを操作しているか不明確。
    - 状態（いいねした/してない）によってURIが変わる。

**良い設計例 (RESTスタイル)**
- リソースを「投稿100番に対する『いいね』という関係性」と捉える。
- `PUT /posts/100/likes/1`
    - 投稿100に、ユーザー1がいいねする（存在しなければ作成、存在すれば更新）。冪等性が保たれる。
- `DELETE /posts/100/likes/1`
    - 投稿100から、ユーザー1のいいねを削除する。これも冪等。

GETでいいね一覧を取得することもできます。
- `GET /posts/100/likes`
- `GET /users/1/likes`

このように、リソースを名詞で定義し、HTTPメソッドで操作を表現することで、統一感のあるAPIが生まれます。

## 🔍 深掘り：プロの視点

### HATEOASの真の価値
RESTの制約の中で最も実践されていないのがHATEOASかもしれません。しかし、その価値は絶大です。

- **従来のAPI**: クライアントは「ユーザーを取得するには`/users/{id}`を叩き、そのユーザーの投稿一覧は`/users/{id}/posts`を叩く」という**APIの仕様書を事前に知っている**必要があります。
- **HATEOAS準拠のAPI**: `/users/123`のレスポンスに、次のようなリンク情報が含まれます。
    ```json
    {
        "id": 123,
        "name": "Taro Yamada",
        // ... 他のユーザー情報
        "_links": {
            "self": { "href": "/users/123" },
            "posts": { "href": "/users/123/posts" },
            "edit": { "href": "/users/123" }
        }
    }
    ```
クライアントは、この`_links`を見て「投稿一覧を取得するにはこのURLを叩けばいいのか」と動的に判断できます。これにより、サーバー側がURIを変更しても、クライアントは仕様書を読み直すことなく追従できる、という究極の疎結合が実現します。

### バージョニング戦略
APIは一度公開すると、簡単には変更できません。機能追加や仕様変更のために、バージョニングが必要になります。
- **URIに含める (主流)**: `/v1/users`, `/v2/users`
    - 分かりやすいが、URIがリソースそのものを指す原則から少し外れる。
- **クエリパラメータ**: `/users?version=1`
- **カスタムヘッダー**: `Accept: application/vnd.myapi.v1+json`
    - 最もRESTfulと言われるが、クライアント側での利用が煩雑。

多くの現場では、シンプルさと分かりやすさからURIにバージョンを含める方法が採用されています。

## 📋 まとめとチェックポイント
- RESTは、Webの技術（HTTP）をベースにした、シンプルでスケーラブルなシステムを構築するためのアーキテクチャ原則。
- API設計は「動詞(RPC)」ではなく「名詞(リソース)」中心で行う。
- URIでリソースを定義し、HTTPメソッド（GET, POST, PUT, DELETE）でそのリソースを操作する。
- **ステートレス**であることが、スケーラビリティの鍵。
- **安全性**（リソース状態を変えない）と**冪等性**（何回やっても結果が同じ）を意識することで、堅牢なAPIになる。
