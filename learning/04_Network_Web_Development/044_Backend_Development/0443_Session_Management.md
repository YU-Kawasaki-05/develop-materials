# セッション管理

## 🎯 この章で学ぶこと
- HTTPがステートレスである理由と、セッション管理の必要性を理解する。
- Cookieベースのセッション管理の仕組みを学ぶ。
- トークンベースの認証（JWTなど）の概念と利点を理解する。
- セッションハイジャックなどのセキュリティリスクとその対策方法を知る。
- サーバーサイドとクライアントサイドでのセッションデータの保存戦略を比較する。

## 🤔 なぜ重要なのか
オンラインショッピングサイトで、商品をカートに入れてページを移動しても、カートの中身が保持されていますよね。この「ユーザーが誰で、何をしているか」をサーバーが覚え続ける仕組みがセッション管理です。

Webの基本プロトコルであるHTTPは「ステートレス（状態を持たない）」です。つまり、サーバーは各リクエストを完全に独立したものとして扱い、前のリクエストを記憶しません。これでは、ログイン状態を維持したり、ショッピングカートを管理したりできません。セッション管理は、このステートレスなHTTP通信において、ユーザーの状態（ステート）を維持するための極めて重要な技術なのです。これがなければ、現代のWebアプリケーションは成り立ちません。

## 📚 基礎概念の理解

### ステートレスプロトコルとセッション
- **ステートレス (Stateless)**: 各リクエストが前のリクエストの情報を引き継がない性質。サーバーは毎回「はじめまして」の状態でリクエストを処理します。
- **セッション (Session)**: ユーザーがWebサイトを訪れてから離れるまでの一連の通信。この期間中、サーバーはユーザーを識別し、状態を維持する必要があります。
- **なぜ必要か**: ログイン状態、ショッピングカートの内容、ユーザー設定など、一連の操作を通じて維持したい情報を管理するためにセッション管理が不可欠です。

### Cookieベースのセッション管理
これは伝統的で広く使われている方法です。
1.  **ユーザーログイン**: ユーザーがIDとパスワードでログインします。
2.  **セッションID生成**: サーバーはユニークな「セッションID」を生成します（例: `xyz123abc`）。
3.  **サーバーサイド保存**: サーバーはセッションIDとユーザー情報（例: ユーザーID、カート情報）を関連付けて、データベースやメモリに保存します。
4.  **Cookie送信**: サーバーはレスポンスの`Set-Cookie`ヘッダーでセッションIDをブラウザに送ります。
5.  **Cookie保存**: ブラウザは受け取ったセッションIDをCookieとして保存します。
6.  **以降のリクエスト**: ブラウザは同じサイトへのリクエスト時に、自動的にCookie（セッションID）を付けて送信します。
7.  **ユーザー識別**: サーバーは受け取ったセッションIDを元に、保存されている情報を参照してユーザーを識別します。

### トークンベースの認証 (Token-Based Authentication)
特にSPA (Single Page Application) やモバイルアプリで主流の方法です。代表的なものにJWT (JSON Web Token) があります。
1.  **ユーザーログイン**: ユーザーがIDとパスワードでログインします。
2.  **トークン生成**: サーバーはユーザー情報や権限、有効期限などを含む「トークン」を生成し、電子署名を付けて改ざんを防ぎます。
3.  **トークン送信**: サーバーは生成したトークンをレスポンス本体でクライアントに送ります。
4.  **クライアントサイド保存**: クライアント（ブラウザやアプリ）は、受け取ったトークンを`localStorage`や`sessionStorage`などに保存します。
5.  **以降のリクエスト**: クライアントはリクエストの`Authorization`ヘッダーにトークンを付けて送信します（例: `Authorization: Bearer <token>`）。
6.  **ユーザー識別**: サーバーは受け取ったトークンの署名を検証し、改ざんがないことを確認します。検証に成功すれば、トークン内の情報（例: ユーザーID）を信頼して処理を行います。

**JWTとCookieベースの違い**: JWTの大きな特徴は、サーバー側でセッション情報を保持する必要がない点です（ステートレス）。ユーザー情報がトークン自体に含まれているため、サーバーはトークンを検証するだけでユーザーを識別できます。これにより、サーバーのスケーラビリティが向上します。

## 💡 実践的な活用

### ハンズオン：Express.jsでのセッション管理
- **課題**: Node.jsのフレームワークであるExpress.jsと`express-session`ライブラリを使って、シンプルな訪問カウンターを実装します。
- **コードサンプル (JavaScript with Express)**:
```javascript
const express = require('express');
const session = require('express-session');
const app = express();

app.use(session({
  secret: 'my-secret-key', // セッションIDの署名に使うキー
  resave: false,
  saveUninitialized: true,
}));

app.get('/', (req, res) => {
  if (req.session.views) {
    req.session.views++;
    res.send(`You have visited this page ${req.session.views} times.`);
  } else {
    req.session.views = 1;
    res.send('Welcome to this page for the first time!');
  }
});

app.listen(3000);
```
- **期待される結果**: ブラウザで`/`にアクセスするたびに、カウンターが増加します。これは`express-session`が自動でCookieを発行し、サーバーサイドで`req.session`オブジェクトに訪問回数を保存・管理してくれるためです。

## 🔍 深掘り：プロの視点

### セキュリティに関する考慮点
- **セッションハイジャック (Session Hijacking)**: 攻撃者が何らかの方法でユーザーのセッションIDを盗み、そのユーザーになりすます攻撃。
    - **対策**:
        - **HTTPSの徹底**: 通信を暗号化し、盗聴を防ぐ。
        - **`HttpOnly`属性**: Cookieに`HttpOnly`属性を付けることで、JavaScriptからのアクセスを禁止し、XSS攻撃によるセッションID窃取を防ぐ。
        - **`Secure`属性**: Cookieに`Secure`属性を付けると、HTTPS通信でのみCookieが送信されるようになる。
- **CSRF (Cross-Site Request Forgery)**: ユーザーが意図しないリクエストを送信させられる攻撃。
    - **対策**: CSRFトークン（リクエストごとに発行される使い捨てのトークン）をフォームに埋め込み、サーバー側で検証する。
- **セッション固定化攻撃 (Session Fixation)**: 攻撃者が用意したセッションIDをユーザーに使わせる攻撃。
    - **対策**: ユーザーがログインに成功したタイミングで、必ず新しいセッションIDを再発行する。

### 保存戦略：どこにセッションデータを置くか？
- **インメモリ**: Webサーバーのメモリ上に保存。高速だが、サーバーを再起動するとデータが消える。複数サーバーでの共有が難しい。
- **データベース (DB)**: MySQLやPostgreSQLなどのDBに保存。永続性があり、複数サーバーで共有できるが、アクセス速度はメモリより遅い。
- **専用キャッシュサーバー (Redis, Memcached)**: インメモリ型の高速なKVS。DBより高速で、複数サーバーでの共有も容易。多くの大規模サービスで採用されています。

## 📋 まとめとチェックポイント
- HTTPはステートレスなため、ユーザーの状態を維持するためにセッション管理が必要。
- Cookieベースのセッション管理は、サーバーが状態を持つ伝統的な方法。
- トークンベース（JWTなど）の認証は、サーバーが状態を持たないモダンな方法で、スケーラビリティに優れる。
- セッションハイジャックやCSRFなどの攻撃を防ぐため、セキュリティ対策（HTTPS, HttpOnly属性など）が不可欠。
- セッションデータの保存場所（インメモリ、DB、Redisなど）は、システムの要件に応じて選択する。
